# Networka upgrade report

24 November 2026 · Networka CLI (`nw`) and Python library · Reviewed commit [`0f37fed`](https://github.com/narrowin/networka/commit/0f37feda6b3405c21aed82d3c3d329c08dbcaf75)

**Classification.** No action/change to the product. The proposed development work is reversible. Publishing a release, changing advertised platform support, and exercising device-changing operations require operator confirmation.

**Problem.** A fresh install of the published Networka fails before it can display help. The committed development environment still passes its tests, and the current release workflow would send a stable tag to TestPyPI.

**Desired outcome.** An operator can install a working release, maintainers can reproduce it with one uv version, and a Scrapli 2 build can demonstrate equivalent behavior on the devices Networka supports.

### Options

ICE multiplies impact, confidence in the estimates, and ease. Higher ease means less implementation and verification work.

| Approach | Impact | Confidence | Ease | ICE |
| --- | --- | --- | --- | ---: |
| Compatibility patch, then toolchain refresh, then Scrapli 2 candidate | 10 · restores installs immediately and gives v2 a controlled route to release | 9 · the patch wheel worked and the refreshed suite narrowed the regression to one test. Device parity is still open | 6 · three bounded changes, with device validation concentrated in the last | **540** |
| Compatibility patch and infrastructure refresh, defer v2 | 6 · restores installs and maintenance, while retaining the legacy driver and its Paramiko ceiling | 9 · exercised both the legacy wheel and the refreshed dependency set | 8 · current transport code and inventories can stay in service | **432** |
| Upgrade everything and publish v2 in one release | 8 · reaches the new stack, but delays repair for existing users | 6 · both package APIs are known. RouterOS behavior and native platform coverage remain unverified | 3 · packaging, terminal UI, release automation, and device regressions must be diagnosed together | **144** |

**Recommendation.** Ship a compatibility patch based on `v0.1.13`, fix release routing, and update the toolchain on `main`. Develop the Scrapli 2 candidate in a separate environment. The published release dates to 4 December 2025. Local and GitHub `main` matched at the 26 December 2025 commit, **51 commits beyond the tag**, including public library and platform changes. Building a patch from the tag gives operators a smaller upgrade to validate. [Published release](https://pypi.org/project/networka/0.1.13/) · [Changes since the release](https://github.com/narrowin/networka/compare/v0.1.13...0f37feda6b3405c21aed82d3c3d329c08dbcaf75)

## 1. Restore installs and fix the release path

1. Put the three verified requirements above in the release package metadata. Consolidate the two Scrapli requirements. Networka imports Paramiko itself for SFTP and SSH inventory parsing. The legacy Scrapli extra requires Paramiko below 4. A lockfile alone cannot constrain someone installing the published wheel. Carry the metadata fix forward to `main`. [Networka manifest](https://github.com/narrowin/networka/blob/0f37feda6b3405c21aed82d3c3d329c08dbcaf75/pyproject.toml) · [Legacy Scrapli release](https://pypi.org/project/scrapli/2026.2.20/)
2. Fix the publish conditions before tagging. Both jobs inspect the full `github.ref` for the letter `a`. Even `refs/tags/v0.1.14` matches because of `tags`. Parse `github.ref_name` once with `packaging.version.Version` after removing the leading `v`. Route the build using its `is_prerelease` value. Align the release script's version validation with the canonical wheel version, including `0.1.14rc1`. The tag predates the automated PyPI jobs, so bring the corrected workflow onto the patch branch before release. The current helper pushes to `main` explicitly. Use a reviewed release-branch procedure for this patch. [Release workflow](https://github.com/narrowin/networka/blob/0f37feda6b3405c21aed82d3c3d329c08dbcaf75/.github/workflows/release.yml) · [Release helper](https://github.com/narrowin/networka/blob/0f37feda6b3405c21aed82d3c3d329c08dbcaf75/scripts/release.sh) · [Version parsing](https://packaging.pypa.io/en/stable/version.html)
3. Build both artifacts. Install each into a clean environment using its published dependency metadata and run the CLI smoke checks. Verify stable and RC routing locally, then verify the trusted publisher settings for the repository, workflow and environments. After operator approval, send the RC to TestPyPI, smoke-test that artifact, and publish a fresh stable version. Preserve the patch artifacts and constraints for rollback. ## 3. Migrate the Scrapli transport

**Use one distribution per environment.** Upstream publishes the same implementation as `scrapli2==2.0.4` and `scrapli==2026.11.12`, both released 12 November 2026. The installed import namespace is `scrapli` in both cases. Use the semantic-versioned distribution for the candidate, pin its first qualification build, and remove the legacy extras and `scrapli-community` from that build. Leaving the community package installed pulls the calendar-versioned distribution back in. Give operators the legacy patch and the v2 candidate in separate environments. [Upstream installation guide](https://carlmontanari.github.io/scrapli/installation/) · [2.0.4 distribution and wheels](https://pypi.org/project/scrapli2/2.0.4/#files) · [Community package metadata](https://pypi.org/pypi/scrapli-community/2025.1.30/json)

| --- | --- |
| Construction and ordinary commands | Reuse the existing synchronous `Transport` contract. Replace legacy `Scrapli(**params)` and `GenericDriver` with `Cli(host, definition_file_or_name=…, auth_options=…, session_options=…, transport_options=…)`. Adapt `send_command` to `send_input` and return `CommandResult(result=response.result, failed=response.failed)`. Keep CLI and SDK outputs and error types stable. Route open, retry, and close through the adapter, including the raw-driver shortcut in `DeviceSession`. Verify pooled reuse and reconnects. ### Device acceptance and rollback

Start with an explicitly selected RouterOS node and Linux node from the existing S3N topology. Run the same read-only command and sequence with each build, compare complete output, and repeat through a reused SDK session. Check an invalid command and a failed login to verify exit status and SDK errors. Add representative IOS and IOS-XE devices before declaring parity for the other two fully implemented platforms. For sequence-only platforms, demonstrate the advertised sequence behavior. [Containerlab topology](https://github.com/narrowin/networka/blob/0f37feda6b3405c21aed82d3c3d329c08dbcaf75/clabs/s3n.clab.yml) · [Running commands](../running-commands.md)

Use an isolated lab file to verify upload, download and checksum behavior. Exercise a benign interactive confirmation before scheduling any reboot or firmware operation on an operator-approved disposable device. The existing lab script selects commands using the optional hardware `platform` field and treats empty output as a warning. Use explicit `nw run` commands and inspect their output, or correct the existing script to select by `device_type` and require the expected result. [Lab script](https://github.com/narrowin/networka/blob/0f37feda6b3405c21aed82d3c3d329c08dbcaf75/scripts/lab_validation.py) · [Device configuration](https://github.com/narrowin/networka/blob/0f37feda6b3405c21aed82d3c3d329c08dbcaf75/src/network_toolkit/config.py)

Promote v2 only after the package, operating-system, and device checks pass for the support being claimed. If a candidate fails, direct the pilot back to the separately installed compatibility release and its known dependency set. Reinstalling the original unconstrained PyPI release would recreate the fresh-install failure.
